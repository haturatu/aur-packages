# AUR 管理の設計

## 対象と要件

AUR RPC のメンテナ検索で `haturatu` の PackageBase を列挙し、3 件を取り込んだ。すべて VCS パッケージのため、定期処理では最新版のビルドを確認し、上流コミットの増加だけでは AUR のバージョンを更新しない。レシピの変更を AUR に公開する場合は、フルビルドの成功を必須にする。

## 構成

| パス | 役割 |
| --- | --- |
| `packages/<pkgbase>/` | AUR に公開するレシピ、パッチ、補助ファイル |
| `configs/<pkgbase>.toml` | VCS または安定版の区別、公開可否、更新元、検証の例外 |
| `.aur/<pkgbase>.json` | AUR の同期元コミットとファイルのハッシュ・実行属性 |
| `aurctl_lib.py` | 取り込み、更新、検証、競合判定、公開の共通処理 |
| `.cache/validated.json` | フルビルド後のレシピと設定のハッシュ。Git 管理対象外 |
| `.github/workflows/aur.yml` | テスト、認証なしのビルド、認証ありの公開 |

設定の自動列挙を採用し、パッケージの追加でワークフローを変更する必要をなくした。Python の標準 TOML パーサーを使うため、共通処理の依存ライブラリはない。バージョン検出は対応サービスの多い nvchecker に任せ、PKGBUILD の実行やメタデータ生成は makepkg に任せる。

## 既存ツールとの比較

nvchecker は GitHub、GitLab、PyPI などの監視を共通設定で扱えるため、安定版の検出に採用した。AUR 公開専用ツールや大規模な独自 CLI の追加はせず、通常の Git clone と fast-forward push で AUR の履歴を保持する。GitHub と AUR の履歴を同じツリーへ結合する必要はない。

初期案の Go と Cobra は、少数の管理コマンドには依存と構成が増えるため採用しなかった。更新 PR を生成して別ワークフローを連鎖させる方式も、今回の自動運用には不要なため採用していない。同一ワークフロー内で検証済みの成果物だけを公開ジョブへ渡すことで、GitHub App や追加の PAT を必要としない構成にした。

## 変更と公開の境界

PR は公開認証へアクセスできない。公開ジョブは管理元の `master` だけで起動し、対象 SHA がまだリモートの `master` と一致することを確認する。ビルドは一時ディレクトリで実行するため、VCS の `pkgver()` が更新したバージョンを管理レシピへ戻さない。

公開時は検証レシピのハッシュを確認する。AUR が取り込み時点のファイルと異なる場合は停止し、他のメンテナの変更を自動で上書きしない。AUR と公開予定のファイルが既に同じ場合は、push せず同期状態を回復する。公開処理は PKGBUILD を source しない。

新規パッケージの初回登録は、レシピを仕上げてフルビルドした後に明示的な `register` コマンドで行う。スケジューラが新しい AUR パッケージを無条件に作成することはない。

旧 `haturatu/ght` の `.github/workflows/aur-update.yml` は、中央のワークフローが成功した後に無効化した。上流 push ごとの `pkgver` 更新と公開元の競合を防ぐため、以後の AUR 公開はこのリポジトリへ集約する。

## 運用上の制約

現在は全件を 1 つの使い捨て Arch コンテナでビルドし、1 件でも失敗すれば公開ジョブを起動しない。パッケージ数が増えて検証時間が問題になった段階で、設定から動的 matrix を生成する構成へ分割できる。

パッケージ単位のクリーン chroot や AUR 依存関係の自動ビルドは実装していない。現在の 3 件ではビルド依存関係を公式リポジトリから取得でき、OpenRC の実行環境を必要とする試験だけを明示的に除外する。

GitHub の 60 日間の無活動によるスケジュール停止には、外部監視または定期的な管理作業で対処する。実行しただけで空コミットを作る処理は設けていない。
