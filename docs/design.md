# AUR 管理の設計

このリポジトリでは、AUR パッケージを一つの場所で管理し、定期的な更新とビルド検証を行っています。

そもそも AUR はパッケージごとに独立した Git リポジトリなので、数が増えてくると同じ更新作業を繰り返すことになります。かといって、すべての上流リリースに合わせて無条件に公開すると、壊れたレシピまで利用者へ渡してしまいます。

なので、**登録・更新・検証・公開を一つの CLI にまとめ、ビルドが終わったものだけ別ジョブで公開する**構成にしています。

## パッケージの種類

最初は AUR RPC のメンテナ検索で `haturatu` のパッケージを列挙し、`-git` の3パッケージを取り込みました。その後、GitHub Release を追跡する `libmmd` も追加しています。

VCS パッケージは利用者の `makepkg` が `pkgver()` を実行するため、上流コミットの増加だけを理由に AUR のバージョンを更新しません。安定版は nvchecker で新しい Release を確認し、`pkgver` とチェックサムを更新します。

## ファイルの役割

| パス | 役割 |
| --- | --- |
| `packages/<pkgbase>/` | AUR へ公開する PKGBUILD、パッチ、`.SRCINFO` |
| `configs/<pkgbase>.toml` | VCS / 安定版の区別、公開可否、更新元、検証例外 |
| `.aur/<pkgbase>.json` | 取り込み時点の AUR コミットとファイルのハッシュ・実行属性 |
| `aurctl_lib.py` | 取り込み、更新、検証、競合判定、公開の共通処理 |
| `.cache/validated.json` | ビルド済みレシピと設定のハッシュ。Git 管理外 |
| `.github/workflows/aur.yml` | テスト、認証なしのビルド、認証ありの公開 |

パッケージ名は設定ファイルから列挙するので、追加のたびに Workflow を増やす必要はありません。

Python の標準ライブラリに TOML パーサーがあるため、`aurctl` 自体は外部 Python 依存を増やしていません。バージョンの検出には nvchecker、パッケージ作成には makepkg を使います。

## 既存ツールを組み合わせる

最初は Go と Cobra で専用 CLI を作ることも考えましたが、必要なのは限られたコマンドだけです。そのための依存と構成が増えるのは避けました。

AUR への公開も特殊な同期サービスではなく、通常の Git clone と fast-forward push です。GitHub と AUR の履歴を無理に一つへ結合することはしません。

更新用 PR を生成して別 Workflow を連鎖させる方式も採用していません。1回の Workflow で検証済みの成果物を公開ジョブに渡せばよく、GitHub App や追加 PAT を使う必要がないためです。

## 検証したものしか公開しない

PR では公開用の認証情報へアクセスできません。公開ジョブは `master` だけで動き、検証対象の SHA が現在の `master` と一致していることを確認します。

ビルドは一時ディレクトリで実行し、VCS の `pkgver()` が生成したバージョンを管理レシピへ戻しません。公開時には検証レシピのハッシュも再確認します。

さらに AUR 側のファイルが取り込み時点から変わっていたら停止します。他のメンテナの更新を無断で上書きしないためです。逆に AUR と公開予定レシピが一致していれば、push をせず同期状態だけを回復します。

公開ジョブでは PKGBUILD を source しません。実行が必要な部分と、公開できる権限を持つ部分を分けるためです。

新しい AUR パッケージの初回登録は、完成したレシピを検証してから `register` で明示的に行います。定期実行でパッケージ名を勝手に登録しない設計です。

以前の `haturatu/ght` にあった `.github/workflows/aur-update.yml` は中央管理へ移した後に停止し、上流リポジトリとこの管理リポジトリから同時に公開しないようにしました。

## この構成の限界

現在は全パッケージを一つの使い捨て Arch Linux コンテナでビルドしています。1件でも失敗すれば公開ジョブには進みません。

パッケージ数が増えて検証時間が問題になったら、設定を元に動的 matrix を組む形へ変更できます。ただし今は、その複雑さを持ち込む必要がありません。

`devtools` によるパッケージ単位のクリーン chroot や、AUR の依存関係を自動でビルドする仕組みはありません。OpenRC のサービス起動試験のように、使い捨て Arch コンテナで行えない検証も明示的に除外しています。

`libmmd` については利用側のアプリを追加でビルドしますが、ソースを取得できないアプリの検証はスキップされます。確認できた範囲を、すべての環境での互換性保証と勘違いしないでください。

GitHub の定期実行は60日間活動がないと無効化される場合があります。無理に空コミットを作る仕組みは入れず、必要なら Actions の状態を確認して再有効化します。
